# 1.3 Resources, String Tables and Type Converters

**Scope.** Every property of a Motif widget that an application or a
user can set is a *resource*.  This chapter describes how resources are
declared, defaulted, looked up and converted, and two Motif-specific
layers on top of Xt's mechanism: *synthetic resources* (values that are
transformed on the way in and out, for example between pixels and
millimetres) and *representation types* (named enumerations with
automatically generated string converters).  It also explains why the
resource *names* are offsets into a character array, and what that
means for binary compatibility.

---

## 1.3.1 The resource table

A class declares its resources as an array of `XtResource`:

```c
/* src/lib/Xm/Primitive.c */
static XtResource resources[] = {
    {XmNunitType, XmCUnitType, XmRUnitType,
     sizeof(unsigned char), XtOffsetOf(XmPrimitiveRec, primitive.unit_type),
     XmRCallProc, (XtPointer)_XmUnitTypeDefault},
    {XmNforeground, XmCForeground, XmRPixel,
     sizeof(Pixel), XtOffsetOf(XmPrimitiveRec, primitive.foreground),
     XmRCallProc, (XtPointer)_XmForegroundColorDefault},
    {XmNtraversalOn, XmCTraversalOn, XmRBoolean,
     sizeof(Boolean), XtOffsetOf(XmPrimitiveRec, primitive.traversal_on),
     XmRImmediate, (XtPointer)True},
    ...
};
```

The seven fields of an entry:

| Field | Example | Meaning |
|-------|---------|---------|
| `resource_name` | `XmNforeground` (`"foreground"`) | The instance name, used in `XtSetArg`, resource files (`*foreground: red`) and UIL. |
| `resource_class` | `XmCForeground` (`"Foreground"`) | The class name; a resource file line `*Foreground: red` sets every resource of that class. |
| `resource_type` | `XmRPixel` (`"Pixel"`) | The representation type: the name under which a converter from `String` is registered. |
| `resource_size` | `sizeof(Pixel)` | Bytes copied into the record. |
| `resource_offset` | `XtOffsetOf(XmPrimitiveRec, primitive.foreground)` | Where in the instance record. `XtOffsetOf` is `offsetof`; a resource may address a *superclass* field (Primitive re-declares `XmNx` at `core.x` to change its type to `XmRHorizontalPosition`, see §1.3.4). |
| `default_type` | `XmRImmediate`, `XmRCallProc`, `XmRString`, ... | How to read `default_addr`. |
| `default_addr` | `(XtPointer)True`, `_XmForegroundColorDefault` | The default, interpreted according to `default_type`. |

Xt builds the effective resource list of a class by concatenating the
tables up the superclass chain; a subclass entry with the same name
overrides its ancestor's.  `XtGetApplicationResources`-style lookups
and `XtCreateWidget` then fill the record from, in order of increasing
priority: the default, the resource database (resource files, the
`-xrm` command line, `XAPPLRESDIR`), and the argument list of the
creation call.

### Default types

`XmRImmediate` stores the value itself in the pointer-sized
`default_addr` (hence the `(XtPointer)True` casts).  `XmRString` points
to a string that is converted by the registered converter, which is how
a default can be `"black"`.  `XmRCallProc` names a procedure that
computes the default at creation time, with access to the widget:

```c
/* src/lib/Xm/Display.c */
void _XmSetThickness(Widget widget, int offset, XrmValue *value)
{
  XmDisplay xmDisplay;
  static Dimension thickness;
  xmDisplay = (XmDisplay)XmGetXmDisplay(XtDisplay(widget));
  if (xmDisplay->display.enable_thin_thickness)
    thickness = 1;
  else
    thickness = 2;
  value->addr = (XPointer)&thickness;
}
```

This is how the Motif shadow thickness is 2 by default but 1 under CDE
(`XmNenableThinThickness` on the `XmDisplay` object), and how
`XmNforeground` defaults to a colour computed from the background
(`_XmForegroundColorDefault`, the Motif colour-derivation algorithm in
`Color.c`).  The `static Dimension` holding the result is a classic
Xt idiom: the caller copies the value out immediately, so one static
per procedure suffices, but it is a hidden piece of shared state that a
multi-threaded caller must hold the lock around (Xt does).

## 1.3.2 Resource names are offsets into one table

The macros `XmNforeground`, `XmCForeground` and `XmRPixel` are not
string literals in this tree.  They are generated by `makestrs` from
[`xmstring.list.in`](../../src/lib/Xm/xmstring.list.in) (1 705 names)
into `XmStrDefs.h`, and the generator has two output modes:

```c
/* src/bin/utils/makestrs.c, WriteHeaderProlog: when XMSTRINGDEFINES is defined */
#define XmNforeground "foreground"
/* IntelABIWriteHeader: the normal case */
externalref const char _XmStrings[];
#ifndef XmNforeground
#define XmNforeground ((char*)&_XmStrings[12345])
#endif
```

and the matching `XmStrDefs.c` defines `_XmStrings` as one character
array holding every name, NUL-separated.  The reasons are historical
but still valid:

- **One copy of each string per process**, instead of one per
  translation unit that uses the macro (pre-C89 compilers and linkers
  did not merge identical string literals).
- **Pointer equality works.**  Xt compares resource names by quark, but
  much of the toolkit compares `XtNxxx` pointers directly; with one
  table, `XmNforeground == XmNforeground` across libraries.
- **Fewer relocations** than a table of pointers: `&_XmStrings[N]` is
  one symbol plus a constant.  The remaining cost is visible in
  [doc/abi-policy.md](../abi-policy.md): 3 114 `R_X86_64_64`
  relocations in libXm are pointers from resource tables into
  `_XmStrings`, because the symbol is exported.

The consequence that matters most: **the order of the list is ABI**.
A program compiled against one `XmStrDefs.h` embeds the numeric
offsets; if the library it runs against has a different `_XmStrings`,
the program's `XmNforeground` points into the middle of some other
string.  This tree re-ordered the table (entries removed and inserted
during the modernisation), so that "1624 of the 1692 `XmC*`/`XmR*`/
`XmS*` macros compiled into 2.3.8 programs name other strings"
([CHANGELOG](../../CHANGELOG.md)); together with the instance-record
change of chapter 1.1 this is why the SONAME is 5.  The rule in
[CONTRIBUTING.md](../../CONTRIBUTING.md) follows: new names go at the
end of the list, never in the middle.

The 1990s-era "SPARC ABI" and "Intel ABI" variants in `makestrs.c`
differ in how the table is declared (array of chars vs. a function
returning the address) and exist to satisfy the shared-library models
of the Unix vendors of the time; this tree uses the Intel ABI form.

## 1.3.3 Type converters

A resource file holds strings; the record holds a `Pixel`, a
`Dimension`, an `XmString` or an enumeration.  Xt bridges the two with
*type converters* registered per (from-type, to-type) pair with
`XtSetTypeConverter`.  libXm registers 34 of them in
[`ResConvert.c`](../../src/lib/Xm/ResConvert.c) (`_XmRegisterConverters`),
among them `String → XmString`, `String → XmFontList`,
`String → XmRenderTable`, `String → KeySym`, `String → XmStringTable`,
`String → Widget` (by name, searched from the widget being created),
`CompoundText ↔ XmString`, and the unit-aware position and dimension
types of §1.3.4.  Each representation type of §1.3.5 adds one more.

A converter has a fixed signature and, in Motif, a fixed way to deliver
its result:

```c
/* src/lib/Xm/SpinB.c */
static Boolean CvtStringToPositionValue(Display *display, XrmValue *args, Cardinal *num_args,
                                        XrmValue *from, XrmValue *to, XtPointer *converter_data)
{
  XtArgVal value;
  int offset = XtOffsetOf(XmSpinBoxConstraintPart, position);
  Widget w = *((Widget *)args[0].addr);
  if (sscanf(from->addr, "%ld", (long *)&value) != 1) {
    XtDisplayStringConversionWarning(display, (char *)from->addr, XmRPositionValue);
    return False;
  }
  (void)SetPositionValue(w, offset, &value);
  _XM_CONVERTER_DONE(to, int, (int)value, ;)
}
```

Three details repay attention:

1. **Converter arguments.**  The converter needs the widget (to read
   the child's `XmNminimumValue` and `XmNincrementValue`).  Xt passes
   extra arguments described by an `XtConvertArgRec` list given at
   registration; `{XtBaseOffset, (XtPointer)0, sizeof(int)}`
   (`selfConvertArgs`) asks for the bytes at offset 0 of the widget
   record, that is, the `self` pointer of `ObjectPart`, which is the
   widget itself.  The converter then reads it back with
   `*((Widget *)args[0].addr)`.
2. **The `to` protocol.**  Xt's converter contract is two-phase: if the
   caller passed a buffer (`to->addr != NULL`) the converter must check
   `to->size` and store the value, or set `to->size` to what it needs
   and return `False`; if the caller passed no buffer, the converter
   returns the address of a static of its own.  The macro
   `_XM_CONVERTER_DONE` in [`XmP.h`](../../src/lib/Xm/XmP.h) encodes
   this once so that every converter in the library gets it right.
3. **Caching.**  `XtCacheNone` is passed because the result depends on
   the widget; converters whose result depends only on the string and
   the display (`String → Pixel`) use `XtCacheByDisplay`, and those
   that allocate (`String → XmString`) register a destructor so that Xt
   can free cached values when the last reference goes away.

## 1.3.4 Synthetic resources and unit types

Motif lets the application work in units other than pixels
(`XmNunitType`: pixels, 100ths of a millimetre, 1000ths of an inch,
100ths of a point, font units) and reports some values differently
from how they are stored.  Xt has no hook for transforming a value on
the way in and out, so Motif adds one: the *synthetic resource* lists
in the Primitive, Gadget and Manager class parts (`syn_resources`,
`syn_constraint_resources`).

```c
/* src/lib/Xm/XmP.h */
typedef struct _XmSyntheticResource {
  String resource_name;
  Cardinal resource_size;
  Cardinal resource_offset;
  XmExportProc export_proc;   /* called by XtGetValues, converts record -> caller */
  XmImportProc import_proc;   /* called on XtSetValues/creation, converts caller -> record */
} XmSyntheticResource;
```

The machinery in [`Synthetic.c`](../../src/lib/Xm/Synthetic.c) hooks
`get_values_hook` (`_XmPrimitiveGetValuesHook`, which Primitive's class
record installs) and is called from the `set_values`/`initialize`
pre-hooks of chapter 1.2 (`_XmPrimitiveImportArgs`).  For every
argument whose name is in the synthetic list it calls the import or
export procedure.  The unit conversion procedures are in
[`ResInd.c`](../../src/lib/Xm/ResInd.c): `XmeToHorizontalPixels`
converts the caller's value from the widget's `XmNunitType` into
pixels using the screen's resolution (`WidthOfScreen`/`WidthMMOfScreen`),
and `XmeFromHorizontalPixels` does the reverse.  This is why
`XmNx`, `XmNwidth` and the margins are re-declared in Primitive's
resource table with the types `XmRHorizontalPosition` and
`XmRHorizontalDimension`: those types have converters that parse unit
suffixes (`"2.5mm"`, `"12pt"`, `XmeParseUnits`) and know which axis to
scale on.

The SpinBox uses the same mechanism for something other than units: a
child's `XmNposition` is stored as a *value* but may be presented as an
*index* when `XmNpositionType` is `XmPOSITION_INDEX`:

```c
/* src/lib/Xm/SpinB.c */
static XmImportOperator SetPositionValue(Widget w, int offset, XtArgVal *value)
{
  XmSpinBoxConstraint wc = SB_GetConstraintRec(w);
  if (SB_ChildIsNumeric(wc) && (!SB_ChildPositionTypeIsValue(wc)))
    *value = wc->minimum_value + (*value * wc->increment_value);
  return (XmSYNTHETIC_LOAD);
}
```

The import procedure returns `XmSYNTHETIC_LOAD` to say "store the
transformed value" or `XmSYNTHETIC_NONE` to say "I stored it myself".

*Trade-off.* Synthetic resources keep the stored representation
canonical (pixels, values) so that the layout code never has to think
about units, at the cost of a second, Motif-only resource table per
class that must be kept in sync with the Xt one, and a transformation
that silently rounds (100ths of a millimetre to integer pixels).

## 1.3.5 Representation types: enumerations with names

Dozens of Motif resources are small enumerations: `XmNarrowDirection`
is `XmARROW_UP`, `XmARROW_DOWN`, ...; `XmNalignment`,
`XmNorientation`, `XmNshadowType`, `XmNselectionPolicy`.  Each needs a
`String →` converter so that `*arrowDirection: ARROW_UP` works in a
resource file and in UIL.  Writing a converter per enumeration would be
error-prone, so Motif 1.2 added the *representation type registry* in
[`RepType.c`](../../src/lib/Xm/RepType.c): a table of
`{ type name, value names, optional values, count }` records, one
generic converter, and a public API (`XmRepTypeRegister`,
`XmRepTypeGetId`, `XmRepTypeValidValue`, `XmRepTypeGetNameList`) that
applications use for their own enumerations and that UIL and the
editres protocol use to validate values.

```c
/* src/lib/Xm/RepType.c, one entry of _XmStandardRepTypes */
    {
        XmRArrowDirection,
        (String *)ArrowDirectionNames,   /* {"arrow_up", "arrow_down", "arrow_left", "arrow_right"} */
        NULL,                            /* values: NULL => the index is the value */
        XtNumber(ArrowDirectionNames),
        FALSE,
    },
```

The generic converter is a linear scan of the names with a
case-insensitive comparison that also ignores an `Xm` prefix, so that
`"XmARROW_UP"`, `"ARROW_UP"` and `"arrow_up"` all match:

```c
static Boolean ConvertRepType(Display *disp, XrmValue *args, ...)
{
  ...
  while (Index < Record->num_values) {
    if (XmeNamesAreEqual(in_str, Record->value_names[Index])) {
      ...
        unsigned char conversion_buffer;
        conversion_buffer = (unsigned char)((Record->values) ? Record->values[Index] : Index);
        _XmProcessUnlock();
        _XM_CONVERTER_DONE(to, unsigned char, conversion_buffer, ;)
    }
    ++Index;
  }
```

The registry id is passed to the converter as its one converter
argument (`XtImmediate`), which is how one C function serves every
enumeration.  A *reverse* converter (`ReverseConvertRepType`, value to
name) is registered on request (`XmRepTypeAddReverse`) and is what
`XmRepTypeGetNameList` and resource editors use.

Complexity: O(k) string comparisons per conversion for an enumeration
of k values, done once per resource-file lookup and then cached by Xt
(`XtCacheAll`); negligible.  The design's real value is uniformity: a
new enumeration costs a names array and one table entry, and the
"mapped" variant (`values != NULL`) handles enumerations whose numeric
values are not 0..k−1, such as the bit-mask style `XmNarrowSensitivity`.

Most enumerations are stored in an `unsigned char`; the three that
live in an `int` (`XmRID_EDIT_MODE`, `XmRID_WHICH_BUTTON`,
`XmRID_FONT_TYPE`) are special-cased in the converter.  Getting the
size wrong is a silent memory corruption on a big-endian machine, which
is one of the reasons this tree's CI builds and tests on s390x.

## 1.3.6 Resources and the UIL compiler

The UIL compiler must know every resource of every class, its type and
its default, in order to type-check `arguments { XmNwidth = 10; }` and
to emit the UID records that Mrm turns into `XtSetArg` lists.  It gets
that knowledge not from the headers but from
[`motif.wml`](../../src/bin/wml/motif.wml), the Widget Meta-Language
description, from which `wml` generates the compiler's keyword tables
at build time ([README](../../src/bin/wml/README)).  A resource that
exists in `xmstring.list.in` but not in `motif.wml` is therefore
invisible to UIL; adding a resource to a widget is a three-file change
(the class source, the string list, the WML description).

## 1.3.7 Summary of costs and benefits

| Mechanism | Benefit | Cost |
|-----------|---------|------|
| Xt resources | One declaration serves defaults, resource files, UIL, editres, `XtSetValues`. Resource files let users and system administrators restyle programs without recompiling. | Every lookup is by string/quark; creation of a widget walks the merged table and the resource database (Xt caches the per-class list). Positional `XtResource` initialisers are easy to get wrong (`resource_size` vs. the field's real size). |
| `_XmStrings` table | One string per name per process; pointer comparison; fewer relocations. | The table order is ABI; a re-ordered table means a new SONAME. |
| Type converters | Any representation can be made file-settable; converters compose (`String → CompoundText → XmString`). | The two-phase `to` protocol is subtle (`_XM_CONVERTER_DONE` exists because of it); cache policies must match what the converter depends on. |
| Synthetic resources | Unit independence; canonical stored values. | A second resource table per class; silent rounding. |
| Representation types | One generic converter and a public registry for every enumeration; UIL and editres validation for free. | A linear scan per conversion; the three int-sized types are a hard-coded special case. |
